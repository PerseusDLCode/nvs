:PROPERTIES:

:DEPENDS: citation-resolution

Blocks the Tier 3-5 full-text search task (see
[[file:doc/forum.org::#citation-resolution][#citation-resolution]] and
[[file:doc/citation-resolution/tier3_5_triage_with_pages.org][the triage file]]). Do not proceed with the 83-item search batch
until this is resolved.

One pilot case (Davies) against public web resources found: the work
is digitized but OCR quality on 18th-c. long-s typography defeats
literal phrase search; HathiTrust's page-turner is =robots.txt=-
blocked for direct fetch and its public search covers only a subset
of the collection; multiple competing digitizations of the same work
complicate matching regardless.

Likely answer: Institutional Books 1.0, the actual IDI dataset
(https://institutional.org/institutional-books) — same Harvard/
Google Books scans HathiTrust draws from, but explicitly "refined
for accuracy and usability." Two HuggingFace repos exist: a
metadata-only one (confirmed SQL-queryable via DuckDB WASM in the
HF Data Studio) and a "full version" — unconfirmed whether the
latter carries searchable body text or only richer metadata. The
site's Tools page (https://institutional.org/tools) is unexplored.[fn:1]
License note for later: non-commercial, "Early-Access, provisional
terms" — fine for research use, worth remembering if anything from
this project is ever published or distributed.

Next steps:
1. Check institutional.org/tools and the full (non-metadata)
   HuggingFace dataset for actual text content, not just metadata.
2. If promising, re-run the 3-case pilot (Davies, Tollet/Waterford,
   Ritson p.170) against IDI directly before scaling to all 83.
3. Separately: check with Perseus researchers on what access they already
   have or have used, in case this is a solved problem elsewhere in
   the project.

Look at the RawToChunks parser class in @src/hypervariorum/nvs/parsers.py.
The parse() method, as implemented, does not work properly; it appears to skip
lines, and there may be additional flaws.

Fix this method. It should process a raw text file to which start and
stop markers have been added: between those markers, the method should extract
everything between the <CC> and </CC> tags and generate a <chunk>
element. The opening <chunk> tag should record data from the running
head (denoted with <HE></HE> tags), specifically, the page number, the
act number, and the scene number. The method should accumulate the
chunks in a list (self.chunks).

Add a new method to serialize self.chunks to a file.

Write tests to verify that the parse() method is extracting all the
text between the <CC> and </CC> tags. Test to make sure it isn't
picking up lines outside the <CC> </CC> tags.  Test to make sure the
running head is being properly parsed into page number, act number,
and scene number values.

Root cause was a line-by-line state machine that silently mis-parsed
single-line =<CC>...</CC>= blocks (1 of 2,703 occurrences in the
corpus); replaced with a regex scan over the START/STOP region. See
=src/hypervariorum/nvs/parsers.py= and =tests/test_parsers.py=,
=feature/reimplement-parsing-chunk-extraction= (merged). Also see
[[file:doc/forum.org::#pipeline/two-stage][#pipeline/two-stage]] for
the Stage 1/Stage 2 design this fed into.

* TODO Implement Stage 2: ChunkConsolidator
:PROPERTIES:
:CUSTOM_ID: pipeline/chunk-consolidator
:DEPENDS: pipeline/chunk-dataclass
:END:
See [[file:doc/forum.org::#pipeline/two-stage-stage-two][#pipeline/two-stage-stage-two]] for full design rationale.

Implement =ChunkConsolidator= in =src/hypervariorum/nvs/parsers.py=
(stub already present). It takes =list[Chunk]= and produces a list
of =Annotation= objects (new dataclass: =act=, =scene=, =line=,
=line_from=, =line_to=, =lemma=, =commentary= fields; all =str | None=
except where obviously typed otherwise).

Algorithm:
1. For each chunk, check whether its content contains a =<C>...</C>=
   line using =re.search(r"^\s*<C>.*?</C>\s*$", chunk.content, re.MULTILINE)=.
2. If yes (continuation): strip the =<C>...</C>= line and the
   immediately following =<P>= (an encoding artifact). Append the
   text before the first new-annotation =<P>= to the previous
   annotation's =commentary=. Then process any remaining =<P>=
   sections as new annotations (step 3). If there is no previous
   annotation, log a warning and fall through to step 3.
3. If no (normal): apply =split_annotation_chunks= to =chunk.content=,
   then for each non-empty sub-chunk call =parse_lemma= and
   =extract_line_info= to build an =Annotation=. Set =act= and =scene=
   from =chunk.act= / =chunk.scene=. Track the last =Annotation=
   emitted as =open_annotation= for use in step 2.

Move the following functions from =parsing.py= into =parsers.py=
(unchanged):
- =split_annotation_chunks=
- =parse_lemma=
- =_normalize_bracket_lemma=
- =extract_line_info=

Write tests covering:
- Normal chunk produces correct =Annotation= list
- Continuation chunk merges into previous annotation's commentary
- Continuation chunk containing new annotations after the continuation
  text (the p.259 =nettles/cuckoo-flowers= case)
- Multi-page continuation (same =open_annotation= updated twice)
- Chunk with =act=/=scene= =None= (the introduction chunk)

Once tests pass and =ChunkConsolidator= is complete, delete
=parsing.py= and remove its test file (or migrate any tests not
already covered).

downstream depends on the current tag format specifically.

Update =tests/test_parsers.py= for the new contract: chunks are
compared as =Chunk= objects/fields, not by substring-matching
attributes out of a tag string.

Not in scope: Stage 2 itself (splitting chunks into annotations) and
