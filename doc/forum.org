** Parsing raw XML vs treating it as literal text
:PROPERTIES:
:CUSTOM_ID: parsing-raw-xml-vs-plain-text
:ASSIGNEES: Cliff, Claude Chat
:DEPENDS: nvs/parser-malformed-xml-output
:DISPOSITION: adopt
:END:

<2026-07-17 Fri 12:34> Claude Code surfaced a problem in [[file:../src/hypervariorum/nvs/parsing.py][parsing.py]]
(see [[file:../agenda.org::#nvs/parser-malformed-xml-output][the agenda]]). The current implementation treats the input as plain
text and manipulates it with regular expressions; Claude Code is
trying to parse it into XML.  Should we continue to treat the Critical
Commentary sections as plain text or should we try to parse them?

*** Research
I don't think it is possible to parse the input as XML, because it
simply isn't valid XML.  One example: line 2813 in [[file:../raw/shake.var.lear.txt][shake.var.lear.txt]]
begins a comment that extends over a page break. The starting <P> tag
isn't matched with a closing </P> before the <PB>; on line 2837, the
comment continues on the next page with an opening <P>. And there is
no closing </P> for this comment.  In fact, these <P> tags are
actually milestones, not containing elements.

My thought is that we should continue to treat the raw input as text,
not XML.  However, we should attend to the errors Claude Code surfaced
here and verify that our regexes are working properly.

*** Decision
[2026-07-17] Confirmed: treat Critical Commentary as text, not XML,
for the reasons above — =<P>= is a milestone, not a container; this
was never well-formed XML and never will be. Consequences:

1. /Scope/: applies to the eight =shake.var.*= files (the NVS
   variorum editions). =titus.f1.txt= is a different source entirely
   — a First Folio base-text transcription (=<DIV1>=/=<DIV2>=/
   =<HEAD>=/=<STAGE>=/=<LB>=, attributed =<PB>=), not variorum
   commentary, evidently placed in Greg's =raw/= repository for lack
   of a better home. Out of scope for =nvs/parsing.py=; if it's ever
   needed, it wants its own ingestion path, not a stretch of this one.

2. /Milestones/: identify real milestone tags (=P=, =PB=, possibly
   others) explicitly, as a named classification rather than implicit
   regex behavior, so the parser stops expecting close tags for them.
   Inventory tags occurring *inside* =<CC>...</CC>= spans across the
   eight =shake.var.*= files (=extract_elements= already discards
   everything outside =HE=/=CC=, so front-matter tags — =C=, =SHL=
   ("short horizontal line"), and its companions =LHL=/=FHL= ("long/
   full horizontal line") — never reach the parser and aren't
   actionable here) rather than continuing to discover tags one crash
   at a time.

3. /Inline formatting/ (=B=, =I=, =SC=, =G=, =SUB=): escape as literal
   text for now, not modeled as real XML structure. Deliberately
   provisional, not a verdict on the formatting's value — the plan is
   to use exactly this typography (smallcaps, bold, italic) later to
   help identify author names, book titles, and similar bibliographic
   entities within commentary text, which is real interpretive signal,
   not just display styling. Deferring is safe specifically because
   the lxml-based escaping (queued in =nvs/parser-refactor-lxml=) is
   reversible: parse the stored XML, unescape the text, and the
   original transcription codes are recoverable exactly, so nothing is
   lost by waiting.

   Revisit trigger, not left open-ended: when work begins on using
   typographic markers to identify bibliographic entities in
   commentary (connects directly to =citation-resolution= in
   =doc/forum.org=), or once real classifier requirements for
   =commentary= content exist — whichever comes first. Until then,
   keep =B=/=I=/=SC=/=G=/=SUB= as an explicit "known, deferred,
   escape" category in the same tag-classification registry used for
   the milestone fix, not lumped in with genuinely unclassified tags.

4. /Addendum, found verifying =nvs/parser-refactor-lxml=/: of the
   eight =shake.var.*= files, =ham2.txt= has zero =<CC>= tags (410
   =<HE>= tags, none of them wrapping commentary). It's the NVS
   Hamlet appendix volume — bibliography, actor interpretations,
   table of contents, essays — marked up with =<C>=, =<T>=, =<R>=,
   =<CE>=, =<SHL>=, etc. Not out of scope the way =titus.f1.txt= is
   (the parser runs on it correctly and produces valid, trivially
   empty output), but structurally a different kind of document from
   the other seven, in the same family as =titus.f1.txt='s mismatch.
   Likely relevant to =citation-resolution=: if this genuinely is the
   NVS Hamlet bibliography volume, its content — not scattered =CC=
   commentary — may be that task's real source material.
** Escaped tag litter in commentary text may signal unrecognized structure
:PROPERTIES:
:CUSTOM_ID: nvs/commentary-tag-litter-signals-structure
:ASSIGNEES: Claude Chat, Cliff
:SOURCE: adhoc
:DEPENDS: nvs/parser-malformed-xml-output, parsing-raw-xml-vs-plain-text
:END:

While starting implementation of
[[file:../agenda.org::#nvs/parser-malformed-xml-output][nvs/parser-malformed-xml-output]],
found that the escaped tag remnants surviving in generated commentary
text are not just cosmetic litter — at least one instance is a real,
unrecognized structural pattern. Raises the question of whether
others are hiding the same way, and whether this is a regression from
moving away from ad-hoc string matching.

**** Research
[2026-07-27] Empirically, the literal crash described in
=nvs/parser-malformed-xml-output= (=ParseError: mismatched tag= from
stray =<P>= tags) no longer reproduces: all eight
=raw/shake.var.*.txt= files (=titus.f1.txt= excluded, per the existing
scope decision) currently produce well-formed XML that
=load_annotations()= loads successfully on =main=, today. This
appears to be a side effect of =nvs/parser-refactor-lxml=:
=build_annotation_element= writes =lemma=/=commentary= via lxml
=.text=, which auto-escapes =<=/=>=/=&= on serialization — so a stray
unrecognized tag no longer breaks well-formedness, it just survives as
harmless-looking escaped text (e.g. literal =&lt;LB N=96&gt;=
mid-sentence in a =<commentary>= element).

Traced one concrete case in =raw/shake.var.ac.txt=: a bracketed lemma
wrapped in =<C>[...]</C>= (e.g. =<C>[32. <B>Cleopatra</B>]</C>=),
immediately followed by =<P>=, is not an unrecognized *new-annotation*
lemma format the way it first appeared. Checked against the digitized
facsimile of this edition of *Antony and Cleopatra* at the Internet
Archive
([[https://archive.org/details/in.ernet.dli.2015.226433/page/n29/mode/2up][page
8]]): the centered, bracketed lemma repeats the lemma from the
previous page, signaling that the commentary on it continues rather
than starting fresh. Frequency check across the seven
commentary-bearing files: 184 occurrences total (ac 14, coriol 114,
ham 30, lear 1, macb 7, oth 18, rj 0); 179 of 184 (97%) immediately
followed by =<P>=, the remaining 5 by =<BQ>= (a quoted passage
resuming before prose). The parser currently has no way to recognize
this pattern — the continuation text either becomes a garbled orphan
annotation or is silently absorbed into whichever chunk follows,
rather than being correctly appended to the annotation whose lemma it
repeats.

Not yet established: whether the *other* escaped-tag litter (bare
=<P>=, =<LB>=, =<FIG>=, =<FHL>= not preceded by a =<C>[...]</C>=
continuation marker — i.e., ordinary paragraphs simply resuming after
a page or line break with no annotation boundary crossed) is uniformly
benign, or whether some of it hides other unrecognized patterns of the
same kind as the continuation marker. That inventory work — and the
judgment call on whether the shift away from ad-hoc string matching
(toward the current regex-plus-lxml-construction approach) is itself
what let this go unnoticed — is what's being handed to Claude Chat
here, rather than guessed at from the Claude Code side.

Stakes: this directly blocks the current actual goal, processing
citations within commentary text — citation extraction needs
commentary text with trustworthy annotation boundaries first.

**** Research (addendum)
[2026-07-28] Cliff's observation resolves the open question above:
the playtext and the Critical Commentary are paginated
independently. The playtext advances at a roughly fixed rate (so
many verse lines per page); the commentary is elastic — a lemma may
get two words or, per the =tender-hefted= case in
=edge3/topic-classifier-precedent=, a page and a half. When the
commentary hasn't finished by the time the page is full, Furness's
printer cuts it, carries it to the next page, and marks the
continuation by repeating the bracketed lemma — =<C>[...]</C>=
immediately followed by =<P>= — rather than opening a genuinely new
annotation. This is a print convention for stitching a note across a
page break, not an unrecognized annotation format.

This reframes the finding: it is not evidence of a hidden Edge-3-
like judgment call. The traced case (and 179/184, 97%, of the full
population) is directly adjacent to a =<PB>= tag, and the bracketed
lemma text matches the lemma of the annotation that was open when the
page cut. Both conditions are checkable mechanically against the
stream — proximity to =<PB>=, string-match against the preceding
annotation's lemma — with no interpretive reading required. This is
Edge 1 (anchoring): deterministic, computable, previously
misclassified as ambiguous only because the parser's existing
chunk-splitter rule (bracketed-lemma-after-=<P>=-starts-a-new-
annotation) checks the pattern locally rather than relationally
against the preceding annotation and nearest =<PB>=. The remaining 5
occurrences (=<BQ>=-adjacent rather than =<P>=-adjacent) are the same
mechanism applied to a quoted passage resuming rather than prose, not
a separate case.

**** Decision
Let Claude Code run with this and then we'll evaluate the results.

**** Analysis (implementation results)
[2026-07-28] Implemented on
=feature/nvs-parser-continuation-marker-disambiguation= exactly as
specified: =extract_elements= now yields =<PB.../>= tokens
interleaved with =<HE>=/=<CC>= blocks; a new =parse_continuation_marker=
detects a =<C>[...]</C>= chunk immediately followed by =<P>=/=<BQ>=;
the orchestrator merges into the tracked =open_annotation= only when
both conditions hold (immediately after a =<PB>=, and the bracketed

no interpretive judgment" premise. Ran the implementation against
all eight files and classified every =<PB>=-adjacent bracketed-lemma
candidate as matched / lemma-mismatch / no-open-annotation:

| File   | Matched | Mismatch | Expected (survey) |
|--------+---------+----------+--------------------|
| ac     |       5 |        9 |                 14 |
| coriol |      82 |       31 |                114 |
| ham    |       0 |       30 |                 30 |
| lear   |       1 |        0 |                  1 |
| macb   |       5 |        1 |                  7 |
| oth    |       0 |       18 |                 18 |
| rj     |       0 |        0 |                  0 |
| Total  |      93 |       89 |                184 |

=lear= (the play the original spec discussion centered on) matches
100%; =ham= and =oth= match 0%. Two distinct sub-patterns behind the
mismatches, both traced to concrete examples:

1. /The bracketed repeat isn't always verbatim./ Furness elides long
   lemmas with =...= on first mention — e.g. an annotation opens
   =36-38. <B>dram...scandal</B>=, spanning act I, sc. iv — but every
   continuation marker on the five following pages reads =36. 'The
   dram of eale,' &c.=: a different paraphrase, not a literal repeat.
   (=oth='s and the rest of =ham='s mismatches are the same pattern,
   different lemma.) A few cases are near-misses differing only in
   markup, not wording — e.g. marker =144. hoa= vs open =144. <B>hoa</B>=.
2. /"Most recently appended" isn't always "the annotation that was
   open."/ In several cases (all of =ham='s and =oth='s, part of
   =ac='s and =coriol='s) the comparison lands on an *empty* lemma —
   meaning an ordinary, unlabeled =<P>= paragraph-continuation (no
   recognized lemma marker) got appended as its own spurious
   empty-lemma annotation between the real opening and the page
   break, so =open_annotation= by the time of the =<PB>= is one of
   these orphans, not the real one. This is concrete evidence for the
   open question this thread already flagged and left unresolved —
   whether "ordinary" =<P>= litter is uniformly benign. Here, at
   least, it isn't: it silently displaces the continuation-marker
   target.

Both are real judgment calls (how loose should lemma comparison be;
should tracking skip past empty-lemma orphans to find the true open
annotation, and if so how far back) — exactly what the current
Decision was trying to keep out of this task by requiring an exact
string match. Not resolving either unilaterally. Code and tests are
complete and correct against the spec as written (93 genuine merges,
zero regressions); paused here per Cliff pending a fresh Decision on
how to handle the matching gap, rather than continuing on judgment
calls Claude Code shouldn't be making alone. Branch not merged;
=agenda.org='s =nvs/parser-continuation-marker-disambiguation= marked
paused, not done.

**** Research (addendum, on the mismatch pattern)
[2026-07-28] Cliff raised whether the mismatch pattern (=lear= 100%,
=ham=/=oth= 0%, =macb= 71%, =ac= 36%, =coriol= 72%) reflects different
Furness volumes following different editorial/typesetting policies,
rather than one uniform convention. Checked the actual publication
history before reasoning further from the numbers:

| File   | Play               | Published | Editor                          |
|--------+---------------------+-----------+----------------------------------|
| rj     | Romeo & Juliet      |      1871 | Furness Sr. (his first)          |
| macb   | Macbeth             |      1873 | Furness Sr.                      |
| ham    | Hamlet              |      1877 | Furness Sr.                      |
| lear   | King Lear           |      1880 | Furness Sr.                      |
| oth    | Othello             |      1886 | Furness Sr.                      |
| ac     | Antony & Cleopatra  |      1907 | Furness Sr. (son assisting since 1901) |
| coriol | Coriolanus          |      1928 | Furness Jr. ALONE, 16 yrs after Sr.'s death |

One clean fact supports the hypothesis: =coriol= is not a Furness Sr.
volume at all — it's the first New Variorum Coriolanus, produced
solely by Furness Jr. in 1928, a different generation and production
era entirely. But the hypothesis doesn't survive contact with the
rest of the table: if the split were simply Sr.'s convention vs.
Jr.'s, =ham= (1877) and =oth= (1886) — both squarely Sr., both close
in date to =lear= (1880) — should pattern with =lear=. Instead they're
the *worst* matches in the set (0%), worse than =coriol=, the one
volume Sr. never touched. A clean editor-generation story predicts
roughly the opposite ranking from what the data shows.

So: real pattern, probably not reducible to "who edited it." Worth
separating the two failure sub-patterns Claude Code already
identified, because they likely have different causes and need
different responses:

1. /Genuine print-convention variation/ — the traced =ac= case where
   the resumed lemma is a paraphrase (=36. 'The dram of eale,' &c.=)
   rather than a verbatim repeat of the opening lemma
   (=36-38. dram...scandal=). If this is a real habit of a particular
   compositor or editorial moment, it's an actual fact about 19th/
   20th-c. print-shop practice, not noise — worth documenting as such
   even if it complicates the matching rule.
2. /Parser-tracking artifact, unrelated to any editorial policy/ — an
   ordinary, unlabeled =<P>= paragraph-continuation misclassified as
   a spurious empty-lemma annotation, displacing the real "open
   annotation" before the page-break arrives. No Furness editor, Sr.
   or Jr., ever intended a bare paragraph break to open a nameless
   note — this is the chunk-splitter's local-lookahead weakness
   showing up more in some files than others, not a print convention
   to accommodate.

Next step before resolving the Decision on the matching gap: pull 3-4
concrete traced examples from =ham= and =oth= (real text around a
=<PB>=, the way the =ac= case was traced), not just the classification
counts, to see directly whether those files' mismatches are genuinely
paraphrase (supports #1, informs how loose lemma-matching needs to
be) or genuinely orphan-displacement (supports #2, and is simply a
bug to fix — skip past empty-lemma orphans when tracking the open
annotation — independent of whatever gets decided about #1).

**** Research (addendum, traced examples from ham/oth)
[2026-07-28] Pulled concrete examples per the "next step" above, tracing
each mismatch back to the true original bracketed lemma (not just the
parsed =open_lemma= field) by grepping its first occurrence in the raw
text. This changes the picture: the "orphan-displacement" count from the
matched/mismatch table is an overcount, and the "paraphrase" cases split
into two genuinely different sub-patterns, only one of which is really a
paraphrase.

1. /Cosmetic quoting — same words, decorative punctuation added/. =ham=,
   =<PB N=147>=: original =<P>181. <B>good kissing carrion</B>]=
   (no quotes); continuation marker =<C>[181. '<B>good kissing
   carrion.</B>']</C>=. Same for =<PB N=163>=: original =<P>320.
   <B>inhibition</B>]=; marker =<C>[320. '<B>inhibition.</B>']</C>=.
   The wording never changes, only curly quotes and a trailing period get
   added on the continuation-page repeat. A punctuation-insensitive
   comparison (strip quotes/terminal punctuation, compare the rest)
   would catch both of these correctly.

2. /Elision on the original, expansion on the marker — genuinely
   different text, but traceable to one editorial habit/. =ham=,
   =<PB N=83..87>= (the already-known =dram of eale= case): original
   =<P>36-38. <B>dram...scandal</B>]= (Furness's own =...=-elision
   convention for a long lemma); marker =<C>[36. '<B>The dram of
   eale,</B>' &amp;c.]</C>= on all five following pages. Same pattern in
   =oth=, =<PB N=6,7,8>=: original =<P>22, 23. <B>Florentine, . . .
   Wife</B>]= (elided with =. . .=, not =...=, but the same convention);
   marker =<C>[22, 23. '<B>Florentine, (A Fellow almost damn'd in a
   faire Wife).</B>']</C>= on all three following pages. And =oth=,
   =<PB N=31>=: original =<P>16. <B>double</B>]= — here the original
   isn't even elided, just terse — the continuation-page marker instead
   quotes the fuller phrase =<C>[16. '<B>As double as the Dukes.</B>']</C>=.
   All three are the *same* underlying fact: Furness's original bracket
   is a short catchword or an elided phrase, and the continuation-page
   printer's bracket is a fuller quoted rendition of the same lemma —
   not an unrelated paraphrase, but not recoverable by any amount of
   punctuation-stripping either, since the actual word count differs.

3. /What looked like orphan-displacement turned out to include a
   disguised elision case./ Walking back from the =oth= =<PB N=6>=
   Florentine marker past the immediate empty-lemma =open_lemma= to the
   *nearest non-empty* annotation lands on =22. <B>Cassio</B>= — which
   does not match the marker either. Grepping the true first occurrence
   shows the real antecedent is =22, 23. Florentine, . . . Wife]=
   (case 2 above) — several annotations further back than the nearest
   non-empty one. So "skip empty-lemma orphans and take the next
   non-empty lemma" is not a reliable fix by itself: it can land on a
   real but different intervening annotation. Whether =22. Cassio= is
   itself a genuine top-level annotation interrupting the Florentine
   discussion, or an artifact of the same chunk-splitter over-triggering
   on an in-passage lemma reference, isn't established by this trace and
   would need its own look.

Net reframing of Claude Chat's two-category split: cosmetic-quoting
mismatches (category 1) are real and separable — a normalized comparison
handles them. But categories "genuine paraphrase" and "orphan-
displacement" turn out not to be independent: in every traced case, the
non-cosmetic mismatch is the *same* elision-vs-expansion habit (case 2),
and naive orphan walk-back doesn't reliably recover it (case 3) because
the true antecedent isn't always "the nearest real lemma," it's
specifically "the annotation whose elided lemma the marker is expanding"
— which needs elision-aware matching (e.g. compare the marker's lemma
against each candidate with mid-string =...=/=. . .= treated as a
wildcard, walking back as far as needed) rather than either exact-match
or nearest-neighbor.

** Convert inline NVS markup to real XML elements
:PROPERTIES:
:CUSTOM_ID: nvs/inline-xml-conversion
:ASSIGNEES: Claude Code, Cliff
:SOURCE: chat/2026-08-04
:DEPENDS: nvs/commentary-tag-litter-signals-structure, parsing-raw-xml-vs-plain-text
:END:

The =<lemma>= and =<commentary>= elements in =annot.xml= currently
store NVS inline tags as escaped text (=&lt;SC&gt;Walker&lt;/SC&gt;=
etc.), because =ChunkConsolidator= builds them via lxml's =.text=
assignment, which auto-escapes. This makes the output harder to read
and makes =<SC>= — the citation-name marker the =citation-resolution=
thread is built around — invisible to XPath and to any downstream
processing.

*** Research
[2026-08-04] Five inline tag types occur inside =<lemma>= and
=<commentary>= content (established in prior corpus survey):

| NVS tag | Likely meaning | Target encoding         |
|---------+----------------+-------------------------|
| =<B>=   | bold           | =<hi rend="bold">=      |
| =<I>=   | italic         | =<hi rend="italic">=    |
| =<SC>=  | small caps     | =<hi rend="smallcaps">= |
| =<SUB>= | subscript      | =<hi rend="subscript">= |
| =<G>=   | Greek (likely) | =<hi rend="greek">=     |

=SC= mapping is conservative: it may serve purposes other than
citation names, and mapping to =<name>= would be interpretive at
this stage. =G= similarly mapped to =rend="greek"= rather than
=<foreign xml:lang="grc">= until its use is verified across the
corpus. All five map uniformly to =<hi rend="...">=, which is
TEI-compatible and reversible.

Implementation constraint: the raw NVS text contains HTML-like
entities (=&lquo;=, =&rquo;=, =&mdash;=, =&amp;=, etc.) that are
not standard XML entities. Attempting to parse the raw content as
XML will fail on these. The right approach is a regex-based scan
that lifts the five known inline tags into real lxml child elements
while leaving everything else — entities, punctuation, unrecognized
tags — as text, without attempting a full XML parse.

*** Decision
[2026-08-04] Adopt the =<hi rend="...">=  mapping above for all five
tag types. Use a regex-based inline parser rather than an XML parse
of raw content. See =nvs/inline-xml-conversion= in =agenda.org= for
the implementation spec.

[2026-08-04] Implemented and verified against the full =lear= corpus
(0 escaped =&lt;SC&gt;= remaining, 4677 =<hi>= elements, well-formed,
round-trips through =load_annotations()=). See
[[file:../agenda.org::#nvs/inline-xml-conversion][#nvs/inline-xml-conversion]]
for implementation notes and =feature/nvs-inline-xml-conversion=.
Closing.

** Citation Resolution
:PROPERTIES:
:CUSTOM_ID: citation-resolution
:ASSIGNEES: Cliff, Claude Chat
:SOURCE: chat/2026-07-21
:DISPOSITION: defer
:END:

Attempting to link citations in Furness's commentary (the =<SC>=
apparatus) to bibliographic sources, ultimately to check them against
Harvard's IDI holdings. Started as a request to parse the English
bibliography into TEI =<bibl>=; ended up somewhere quite different.

**** Research
[2026-07-21] The bibliography itself resists a parser — inconsistent
author-signaling (=AUTHOR:=, =Edited by=, anonymous), continuation
notes parasitic on head entries, ditto-marks, date ranges — but the
real finding came from sampling actual =<annotation>= commentary
rather than the bibliography alone: citations there aren't just
varied in locator form (bare name / titled / page-only / section-§ /
s.v.), they're varied in *syntactic role* (source, cross-reference,
co-citation, editorial voice), and role isn't recoverable from
adjacent punctuation. This is the Schmidt-Sciences-relevant finding:
this material needs actual reading comprehension, not pattern
matching. Full argument in [[file:concepts.org][concepts.org]] (Attribution Principle,
edge taxonomy), distilled from the 2026-07-06 conversation.

** Edge 3 design precedent: IDI's LC topic classifier
:PROPERTIES:
:CUSTOM_ID: edge3/topic-classifier-precedent
:ASSIGNEES: Cliff, Claude Chat
:SOURCE: chat/2026-07-22
:DEPENDS: citation-resolution
:DISPOSITION: document
:END:

Cliff's July 21 observations on IDI's published tools
([[file:../agenda.org::#corpus/access-feasibility][agenda.org]], footnote 1) surfaced their Topic Classification Model.
Question: does its approach bear on Edge 3 (argument-relation
classification — rebuts/refutes/extends/concedes/qualifies/silently
absorbs/&c.), which citation-resolution deliberately deferred?

**** Research
[2026-07-22] The IDI model
([[https://huggingface.co/institutional/institutional-books-topic-classifier-bert][institutional-books-topic-classifier-bert]]) is a fine-tuned BERT
text-classifier, single-label, over the 21 fixed top-level classes of
the Library of Congress Classification Outline, trained on
bibliographic metadata (title/author/year/general note — not full
text) against an abundance of pre-existing gold labels: nearly every
catalogued volume already carries an LC class from a century of
professional cataloging. Closed taxonomy, single-item, mostly
surface-lexical signal (a title with "analytical geometry" is
obviously SCIENCE without reading past the title page).

That shape maps reasonably well onto our =comment_type= axis
(textual_emendation / glossarial / interpretive / source_study /
performance / biographical) — also a closed, small, single-item
taxonomy, plausibly distillable into a cheap supervised classifier
*eventually*, once we have gold labels from some other source.

It does not map onto =argument_relation=, for three reasons:

1. /No ground truth exists./ LC classification has a century of
   labels to train on. Nobody has labeled "this 1852 note rebuts that
   1783 note" at scale, and concepts.org is explicit that the
   taxonomy itself is a theory, not a settled fact — there is nothing
   to supervise-train against yet.
2. /It's relational, not single-item./ Their classifier takes one
   book, emits one label. Argument-relation classification needs two
   comments in relation, often pages or acts apart, sometimes with
   the relation never stated outright (=silently_absorbs=). A fixed-
   window single-input classifier has no natural way to hold both
   comments at once without scaffolding their problem never required.
3. /The softmax confidence score is a live specimen of
   Arnold-as-softmax./ =\{'label': 'SCIENCE', 'score': 0.9997\}= looks
   like epistemic humility but is just distance from a trained
   decision boundary — structurally incapable of saying "none of
   these fit, and here is why," which is exactly what
   =resists_classification= requires. Worth citing this model
   directly in concepts.org's failure-mode bestiary as a real
   instance of the pattern, not a hypothetical one.

Where this genuinely is useful: their technical report (§4.5, cited
on the model card) documents a real expensive-judgment-to-cheap-
classifier distillation workflow. That's a legitimate future move for
Edge 3 too, but only in that order — run the expensive model on
argument-relation classification first, accumulate its judgments as a
working dataset, and only then consider whether a distilled small
classifier is worth building for scale. The topic classifier is
evidence the distillation step is tractable once labels exist; it is
not evidence that the labeling step can be skipped.

Replace =parsing.py= with a two-stage functional pipeline, following
Unix pipe logic: each stage does one thing and passes clean output
to the next.
*** Stage 1
*Stage 1* (=parsers.py=, =Parser= class, already drafted): extract
=<CC>= blocks from the raw NVS text, attaching act, scene, and page
number metadata parsed from the intervening =<HE>= running heads.
Output is a list of chunks, each carrying enough context that Stage 2

*** Research

[2026-07-31] The key design rationale: act and scene tracking belongs
in Stage 1 because it requires reading the running heads, which are
an artifact of the raw file format. Stage 2 should work on structured
content only. Line numbers in lemmas are sufficient for annotation
identity once act/scene is inherited from the chunk metadata.

One open question before Stage 2 is built: the intermediate
representation between stages. Two options:

- *Raw strings* (current =parsers.py= approach): =<chunk>= elements
  with attributes. Inspectable, writable to a file, Unix-idiomatic.
  Stage 2 must parse attributes back out of strings.

- *Dataclass* (=Chunk= with =act=, =scene=, =page_number=, =content=
  fields): type-safe, no re-parsing. Less directly inspectable but
  the natural Python contract between two stages in the same process.

This choice should be settled before Stage 2 is implemented; it is
the interface contract between the two stages.

**** Research

[2026-08-01] Examined real corpus output (=chunks.txt= from Lear,
~7500 lines). Key findings:

*Continuation detection is simple.* =<C>...</C>= appears only as a
centred line at the start of a continuation chunk's content — never
in any other context in the corpus. No lemma extraction or comparison
is needed; a single regex suffices:
#+begin_src python
r"^\s*<C>.*?</C>\s*$"
#+end_src
(with =re.MULTILINE=). The =<P>= immediately following =</C>= is an
encoding artifact — strip it together with the =<C>...</C>= line and
append what remains to the previous annotation.

*Continuation chunks can contain new annotations.* The chunk at p.259
continues annotation =4. nettles, cuckoo-flowers= but then starts two
new sub-annotations (=4. nettles]= and =4. cuckoo-flowers]=).
=parsing.py='s =continue= statement silently lost these. The fix:
after merging the continuation text, run remaining =<P>= sections
through normal annotation processing. =split_annotation_chunks=
already produces the right split.

*Multi-page continuations are real.* Annotation =91. Enter Fool.=
spans three pages (pp. 66-68); two consecutive chunks open with
=<C>[91. <B>Enter Fool.]</B></C>=. Handled naturally if
=open_annotation= is always the last annotation emitted — no special
case needed.

*9 continuation markers* in Lear total. Rare but real.

*Functions salvageable from =parsing.py= unchanged:*
- =split_annotation_chunks= — splits =<CC>= content on =<P>=
  boundaries that begin a new annotation; handles the continuation
  case correctly.
- =parse_lemma= — three-pattern fallback; well-tested.
- =_normalize_bracket_lemma= — helper used by =parse_lemma=.
- =extract_line_info= — extracts line/line-range attributes.

These move into =parsers.py= alongside =ChunkConsolidator= (or a new
=annotators.py= if the file grows unwieldy).
