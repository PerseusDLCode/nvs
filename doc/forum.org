** Ingestion vs. model: where NVS-specific code ends
:PROPERTIES:
:CUSTOM_ID: architecture/ingestion-model-classifier-split
:ASSIGNEES: Cliff
:SOURCE: chat/2026-07-15
:DEPENDS: packaging/src-layout-split
:DISPOSITION: adopt
:END:

Proposed while queuing the =bin/= → =src/= packaging task: does the
project need an architectural seam between code that is specific to
parsing the NVS transcriptions and code that operates on the
annotation model generally (graph construction, the AI-assisted edge
classifiers)? Renaming the repo/package to =hypervariorum= (see
=process/collaboration-protocol-v2= above) already signals that the
project is meant to outgrow any one source corpus; this question asks
whether the code layout should say so too.


**** Research
[2026-07-15] Parsing is inherently tied to the idiosyncrasies of one
source format — =parse_annotations_to_xml= is built entirely around
this transcription's =<HE>=/=<CC>= tag conventions, with regex tuned
to how this editor marked up acts, scenes, and lemma ranges. That
code will always be NVS-shaped. Classification and graph operations
are, in principle, source-agnostic: a classifier deciding that one
annotation glosses a particular passage doesn't need to know whether
the annotation arrived via NVS markup or some other encoding. This is
the same seam as MVP's Corpus → Annotations → Views layering:
source-specific ingestion feeding a format-independent model, with
higher layers unaware of provenance.

Proposed layout:

#+begin_example
src/hypervariorum/
  nvs/                  <- NVS-specific: markup parsing, entity conversion
    entities.py
    parsing.py
  model/  (or graph/)   <- source-agnostic: Annotation, the dependency graph
    annotation.py
  classifiers/          <- source-agnostic: the AI-assisted edge classifiers
#+end_example

=nvs/= stays as parochial as the source material demands; =model/=
and =classifiers/= are where the project's actual research claim to
Greg/Perseus lives — "a source-agnostic annotation-graph-and-
classifier engine, currently fed by an NVS parser" rather than
"some NVS-specific code."

Open question, not resolved here: is the ingestion layer meant to
stay singular (=nvs/= just documents provenance, permanently the only
source), or is a second source corpus genuinely anticipated (another
variorum edition, or non-Shakespeare material) — in which case =nvs/=
is the first of a =sources/= family rather than a fixture. Cheap to
decide now; expensive to restructure into later. Does not need to be
answered by building a second parser today, just by naming the
likelihood.

Actionable for Claude Code (once Decision is recorded):
- Fold this layout into the =packaging/src-layout-split= task in
  =agenda.org= rather than treating it as a second refactor.

**** Decision
<2026-07-15 Wed 13:26> I had been wondering if there should be an
entirely separate package, in its own repo, for the code that
interfaces with raw files, and then another repo for higher-level code
that works with annotation objects.  And I'm answering my own
question: that's getting too complex for this stage of the project.

So at the beginning of the project we will assume that we will be
using the Furness editions of the NVS as source texts. Explicitly,
then: ingestion stays singular for now — =nvs/= names the one source
and documents its provenance, rather than being built out as a
=sources/= family. Revisit only if a second source corpus actually
materializes.

The Furness editions don't have to live in this repository, though;
see =external/raw-corpus-dependency= below for that question.

** Parsing raw XML vs treating it as literal text
:PROPERTIES:
:CUSTOM_ID: parsing-raw-xml-vs-plain-text
:ASSIGNEES: Cliff, Claude Chat
:DEPENDS: nvs/parser-malformed-xml-output
:DISPOSITION: adopt
:END:

<2026-07-17 Fri 12:34> Claude Code surfaced a problem in [[file:../src/hypervariorum/nvs/parsing.py][parsing.py]]
(see [[file:../agenda.org::#nvs/parser-malformed-xml-output][the agenda]]). The current implementation treats the input as plain
text and manipulates it with regular expressions; Claude Code is
trying to parse it into XML.  Should we continue to treat the Critical
Commentary sections as plain text or should we try to parse them?

*** Research
I don't think it is possible to parse the input as XML, because it
simply isn't valid XML.  One example: line 2813 in [[file:../raw/shake.var.lear.txt][shake.var.lear.txt]]
begins a comment that extends over a page break. The starting <P> tag
isn't matched with a closing </P> before the <PB>; on line 2837, the
comment continues on the next page with an opening <P>. And there is
no closing </P> for this comment.  In fact, these <P> tags are
actually milestones, not containing elements.

My thought is that we should continue to treat the raw input as text,
not XML.  However, we should attend to the errors Claude Code surfaced
here and verify that our regexes are working properly.

*** Decision
[2026-07-17] Confirmed: treat Critical Commentary as text, not XML,
for the reasons above — =<P>= is a milestone, not a container; this
was never well-formed XML and never will be. Consequences:

1. /Scope/: applies to the eight =shake.var.*= files (the NVS
   variorum editions). =titus.f1.txt= is a different source entirely
   — a First Folio base-text transcription (=<DIV1>=/=<DIV2>=/
   =<HEAD>=/=<STAGE>=/=<LB>=, attributed =<PB>=), not variorum
   commentary, evidently placed in Greg's =raw/= repository for lack
   of a better home. Out of scope for =nvs/parsing.py=; if it's ever
   needed, it wants its own ingestion path, not a stretch of this one.

2. /Milestones/: identify real milestone tags (=P=, =PB=, possibly
   others) explicitly, as a named classification rather than implicit
   regex behavior, so the parser stops expecting close tags for them.
   Inventory tags occurring *inside* =<CC>...</CC>= spans across the
   eight =shake.var.*= files (=extract_elements= already discards
   everything outside =HE=/=CC=, so front-matter tags — =C=, =SHL=
   ("short horizontal line"), and its companions =LHL=/=FHL= ("long/
   full horizontal line") — never reach the parser and aren't
   actionable here) rather than continuing to discover tags one crash
   at a time.

3. /Inline formatting/ (=B=, =I=, =SC=, =G=, =SUB=): escape as literal
   text for now, not modeled as real XML structure. Deliberately
   provisional, not a verdict on the formatting's value — the plan is
   to use exactly this typography (smallcaps, bold, italic) later to
   help identify author names, book titles, and similar bibliographic
   entities within commentary text, which is real interpretive signal,
   not just display styling. Deferring is safe specifically because
   the lxml-based escaping (queued in =nvs/parser-refactor-lxml=) is
   reversible: parse the stored XML, unescape the text, and the
   original transcription codes are recoverable exactly, so nothing is
   lost by waiting.

   Revisit trigger, not left open-ended: when work begins on using
   typographic markers to identify bibliographic entities in
   commentary (connects directly to =bibliography/parser= in
   =agenda.org=), or once real classifier requirements for
   =commentary= content exist — whichever comes first. Until then,
   keep =B=/=I=/=SC=/=G=/=SUB= as an explicit "known, deferred,
   escape" category in the same tag-classification registry used for
   the milestone fix, not lumped in with genuinely unclassified tags.

4. /Addendum, found verifying =nvs/parser-refactor-lxml=/: of the
   eight =shake.var.*= files, =ham2.txt= has zero =<CC>= tags (410
   =<HE>= tags, none of them wrapping commentary). It's the NVS
   Hamlet appendix volume — bibliography, actor interpretations,
   table of contents, essays — marked up with =<C>=, =<T>=, =<R>=,
   =<CE>=, =<SHL>=, etc. Not out of scope the way =titus.f1.txt= is
   (the parser runs on it correctly and produces valid, trivially
   empty output), but structurally a different kind of document from
   the other seven, in the same family as =titus.f1.txt='s mismatch.
   Likely relevant to =bibliography/parser=: if this genuinely is the
   NVS Hamlet bibliography volume, its content — not scattered =CC=
   commentary — may be that task's real source material.
** Escaped tag litter in commentary text may signal unrecognized structure
:PROPERTIES:
:CUSTOM_ID: nvs/commentary-tag-litter-signals-structure
:ASSIGNEES: Claude Chat, Cliff
:SOURCE: adhoc
:DEPENDS: nvs/parser-malformed-xml-output, parsing-raw-xml-vs-plain-text
:END:

While starting implementation of
[[file:../agenda.org::#nvs/parser-malformed-xml-output][nvs/parser-malformed-xml-output]],
found that the escaped tag remnants surviving in generated commentary
text are not just cosmetic litter — at least one instance is a real,
unrecognized structural pattern. Raises the question of whether
others are hiding the same way, and whether this is a regression from
moving away from ad-hoc string matching.

**** Research
[2026-07-27] Empirically, the literal crash described in
=nvs/parser-malformed-xml-output= (=ParseError: mismatched tag= from
stray =<P>= tags) no longer reproduces: all eight
=raw/shake.var.*.txt= files (=titus.f1.txt= excluded, per the existing
scope decision) currently produce well-formed XML that
=load_annotations()= loads successfully on =main=, today. This
appears to be a side effect of =nvs/parser-refactor-lxml=:
=build_annotation_element= writes =lemma=/=commentary= via lxml
=.text=, which auto-escapes =<=/=>=/=&= on serialization — so a stray
unrecognized tag no longer breaks well-formedness, it just survives as
harmless-looking escaped text (e.g. literal =&lt;LB N=96&gt;=
mid-sentence in a =<commentary>= element).

Traced one concrete case in =raw/shake.var.ac.txt=: a bracketed lemma
wrapped in =<C>[...]</C>= (e.g. =<C>[32. <B>Cleopatra</B>]</C>=),
immediately followed by =<P>=, is not an unrecognized *new-annotation*
lemma format the way it first appeared. Checked against the digitized
facsimile of this edition of *Antony and Cleopatra* at the Internet
Archive
([[https://archive.org/details/in.ernet.dli.2015.226433/page/n29/mode/2up][page
8]]): the centered, bracketed lemma repeats the lemma from the
previous page, signaling that the commentary on it continues rather
than starting fresh. Frequency check across the seven
commentary-bearing files: 184 occurrences total (ac 14, coriol 114,
ham 30, lear 1, macb 7, oth 18, rj 0); 179 of 184 (97%) immediately
followed by =<P>=, the remaining 5 by =<BQ>= (a quoted passage
resuming before prose). The parser currently has no way to recognize
this pattern — the continuation text either becomes a garbled orphan
annotation or is silently absorbed into whichever chunk follows,
rather than being correctly appended to the annotation whose lemma it
repeats.

Not yet established: whether the *other* escaped-tag litter (bare
=<P>=, =<LB>=, =<FIG>=, =<FHL>= not preceded by a =<C>[...]</C>=
continuation marker — i.e., ordinary paragraphs simply resuming after
a page or line break with no annotation boundary crossed) is uniformly
benign, or whether some of it hides other unrecognized patterns of the
same kind as the continuation marker. That inventory work — and the
judgment call on whether the shift away from ad-hoc string matching
(toward the current regex-plus-lxml-construction approach) is itself
what let this go unnoticed — is what's being handed to Claude Chat
here, rather than guessed at from the Claude Code side.

Stakes: this directly blocks the current actual goal, processing
citations within commentary text — citation extraction needs
commentary text with trustworthy annotation boundaries first.

** Citation Resolution
:PROPERTIES:
:CUSTOM_ID: citation-resolution
:ASSIGNEES: Cliff, Claude Chat
:SOURCE: chat/2026-07-21
:DISPOSITION: defer
:END:

Attempting to link citations in Furness's commentary (the =<SC>=
apparatus) to bibliographic sources, ultimately to check them against
Harvard's IDI holdings. Started as a request to parse the English
bibliography into TEI =<bibl>=; ended up somewhere quite different.

**** Research
[2026-07-21] The bibliography itself resists a parser — inconsistent
author-signaling (=AUTHOR:=, =Edited by=, anonymous), continuation
notes parasitic on head entries, ditto-marks, date ranges — but the
real finding came from sampling actual =<annotation>= commentary
rather than the bibliography alone: citations there aren't just
varied in locator form (bare name / titled / page-only / section-§ /
s.v.), they're varied in *syntactic role* (source, cross-reference,
co-citation, editorial voice), and role isn't recoverable from
adjacent punctuation. This is the Schmidt-Sciences-relevant finding:
this material needs actual reading comprehension, not pattern
matching. Full argument in [[file:concepts.org][concepts.org]] (Attribution Principle,
edge taxonomy), distilled from the 2026-07-06 conversation.

Drafted an Edge-3 (Argument) classification task spec informed by
that framework, then stepped back from it: premature. What's still
open is Edge 2 (Citation) — genuinely less mechanical than assumed,
but a different kind of judgment than Edge 3's argument-relation
classification. Edge 2 mostly resolves to *period knowledge*
(recognizing that bare "Wright:" means W. Aldis Wright's Clarendon
Lear, 1875), not to interpretive reading of argumentative structure.
Worth keeping this boundary explicit going forward — it's tempting to
reach for the heavier Edge-3 apparatus (mandatory agent/basis/
confidence on every record) when it isn't warranted yet.

Built a resolution cascade for the ~71 bare-colon =<SC>= names
(population from the July 21 pilot): Tier 0 resolves from the
bibliography parse we already have (=Edited by=-pattern entries —
Wright, Moberly, Hudson); Tier 1 is genuinely-excluded complete-Works
editors (Johnson, Steevens, Malone, &c., per Norris's own "surplusage"
footnote); Tiers 2-3 resolve against single/multiple bibliography
entries; Tiers 4-5 are likely variorum-embedded 18th-c. contributors
and genuinely uncertain identities. ~90% resolves at Tiers 0-3; the
open pile (Tiers 3-5) is under 40 names. Full table: [[file:citation-resolution/bare_citation_resolution.org][doc/citation-resolution/bare_citation_resolution.org]].

Extracted and triaged all 112 occurrences of the Tier 3-5 names
(act.scene.line locus, NVS page number via the raw =<PB>=-tagged
transcription, verdict on full-text-search value). 83 are search-
worthy. Several identity corrections came only from reading the
actual citation content, not from name-plausibility: Davies, Dodd,
Wedgwood, Gifford confirmed; Reynolds and Burney reclassified from
"uncertain one-off" to "likely variorum-embedded" on the strength of
their prose register; "Clarke" is probably not a fifth identity at
all but shorthand for Cowden Clarke. Full triage:
[[file:citation-resolution/tier3_5_triage_with_pages.org][doc/citation-resolution/tier3_5_triage_with_pages.org]].

Ran a one-case pilot (Davies) against public web resources to test
full-text search feasibility before committing to all 83: found the
work digitized (Internet Archive) but OCR quality on 18th-c. long-s
typography is bad enough to defeat literal phrase search; HathiTrust's
viewer is =robots.txt=-blocked for direct fetch and its public search
covers only a subset of the collection; multiple competing
digitizations of the same work complicate matching regardless (same
edition-proliferation problem as Walker's /Critical Examination/).

Cliff surfaced Institutional Books 1.0 (institutional.org) the same
session — confirmed as the real IDI dataset, Harvard Law School
Library / Library Innovation Lab, "refined for accuracy and usability."
Unconfirmed whether the metadata-only HuggingFace release carries
searchable body text or only bibliographic/topic fields; the "full"
release and the site's Tools page are unexplored. This is the actual
blocker now — see [[file:agenda.org::#corpus/access-feasibility][agenda.org]].

[2026-07-21] Cliff's call: pause the Tier 3-5 search batch. Do not
scale to the remaining ~80 occurrences until corpus access is
resolved — running them against public web resources the way the
Davies pilot did would waste effort against the OCR/access problem
just demonstrated, not against the citation-resolution problem this
thread is actually about. Confirmed: stay at Edge 2 for now; Edge 3
(argument classification) is a later, separate task, not a natural

** Edge 3 design precedent: IDI's LC topic classifier
:PROPERTIES:
:CUSTOM_ID: edge3/topic-classifier-precedent
:ASSIGNEES: Cliff, Claude Chat
:SOURCE: chat/2026-07-22
:DEPENDS: citation-resolution
:DISPOSITION: document
:END:

Cliff's July 21 observations on IDI's published tools
([[file:../agenda.org::#corpus/access-feasibility][agenda.org]], footnote 1) surfaced their Topic Classification Model.
Question: does its approach bear on Edge 3 (argument-relation
classification — rebuts/refutes/extends/concedes/qualifies/silently
absorbs/&c.), which citation-resolution deliberately deferred?

**** Research
[2026-07-22] The IDI model
([[https://huggingface.co/institutional/institutional-books-topic-classifier-bert][institutional-books-topic-classifier-bert]]) is a fine-tuned BERT
text-classifier, single-label, over the 21 fixed top-level classes of
the Library of Congress Classification Outline, trained on
bibliographic metadata (title/author/year/general note — not full
text) against an abundance of pre-existing gold labels: nearly every
catalogued volume already carries an LC class from a century of
professional cataloging. Closed taxonomy, single-item, mostly
surface-lexical signal (a title with "analytical geometry" is
obviously SCIENCE without reading past the title page).

That shape maps reasonably well onto our =comment_type= axis
(textual_emendation / glossarial / interpretive / source_study /
performance / biographical) — also a closed, small, single-item
taxonomy, plausibly distillable into a cheap supervised classifier
*eventually*, once we have gold labels from some other source.

It does not map onto =argument_relation=, for three reasons:

1. /No ground truth exists./ LC classification has a century of
   labels to train on. Nobody has labeled "this 1852 note rebuts that
   1783 note" at scale, and concepts.org is explicit that the
   taxonomy itself is a theory, not a settled fact — there is nothing
   to supervise-train against yet.
2. /It's relational, not single-item./ Their classifier takes one
   book, emits one label. Argument-relation classification needs two
   comments in relation, often pages or acts apart, sometimes with
   the relation never stated outright (=silently_absorbs=). A fixed-
   window single-input classifier has no natural way to hold both
   comments at once without scaffolding their problem never required.
3. /The softmax confidence score is a live specimen of
   Arnold-as-softmax./ =\{'label': 'SCIENCE', 'score': 0.9997\}= looks
   like epistemic humility but is just distance from a trained
   decision boundary — structurally incapable of saying "none of
   these fit, and here is why," which is exactly what
   =resists_classification= requires. Worth citing this model
   directly in concepts.org's failure-mode bestiary as a real
   instance of the pattern, not a hypothetical one.

Where this genuinely is useful: their technical report (§4.5, cited
on the model card) documents a real expensive-judgment-to-cheap-
classifier distillation workflow. That's a legitimate future move for
Edge 3 too, but only in that order — run the expensive model on
argument-relation classification first, accumulate its judgments as a
working dataset, and only then consider whether a distilled small
classifier is worth building for scale. The topic classifier is
evidence the distillation step is tractable once labels exist; it is
not evidence that the labeling step can be skipped.

**** Reference: a worked example (tender-hefted, II.iv.168)

independently illustrates exactly the citation-resolution difficulty

since it's a better worked example than anything invented for
illustration. Furness's note on "tender-hefted" runs seven citations

- =<SC>Davies</SC>=, bare, no locator — exactly the ambiguous-identity

- =<SC>Knight</SC>: We doubt Steevens's explanation.= — a real,
